# P6 Deployment

**Requirement (PDF, P6):** a way to run the software outside the development environment (Dockerfile, start scripts). The artifacts are generated, consistent with the design, and they must work.

**How it works**

- `generate {guidance}`: the `deployer` (mid) writes a Dockerfile, `run.sh`, `run.ps1` and `DEPLOY.md`, guided by the component or deployment diagram if there is one, plus a smoke command (`python -m todo list`) and how to start the program for real: `start_command` (`python -m todo`), `url` for a web app, up to three `example_commands` for a command-line program, `stop_hint`. The check runs at once.
- Check, by code: every `COPY` source and every `python -m` module exists in the generated code, and the Dockerfile has a `CMD` or `ENTRYPOINT` (`domain/deploy.py`). Then the smoke command starts the program in the Sandbox with the code, without a shell (no pipes or redirection; the schema refuses them); for an interactive program the deployer gives `smoke_input`, which the program reads as standard input (real run s03: a tic-tac-toe game could not be checked before). Exit code 0 passes. Artifact `deployment-check`.
- Run guide, by code: artifact `run-guide` (kind `run_guide`, title "Run it", file `RUN.md` next to `DEPLOY.md`; path `app/RUN.md`). Content: `start_command`, `url`, `example_commands`, `stop_hint`, `checked`, `derived` (`domain/deploy.py: RunGuide`); the text is a short Markdown with the commands in code blocks. The project folder is not in it: the UI knows the folder and puts `cd "<folder>"` in front. A start command or example whose module or script is not in the code is a problem of the check, and so is a start command that still has the check option of the smoke run (`--check`). `checked` is true only when the smoke run passed and started the same module or script. The schema sends a start command back that is not a plain `python ...` command; `RUN.md` as a deployer file is refused, because Wings writes it.
- Taken port, by code: before the smoke run the check asks the sandbox (`Sandbox.port_in_use`, a connect to 127.0.0.1) whether another program already serves the port of the run guide's `url` (`domain/deploy.py: local_port`). If so, `port_taken` is set in the run guide and the check, RUN.md and the check say "Port 8000 was in use by another program when Wings checked...", and the reply adds one line. It is a fact about the computer, not a failure of the deployment: the check still passes. Why (2026-11-25, Windows): a generated `http.server` started on a port an older game still served, because `HTTPServer` sets `allow_reuse_address`, and the browser showed the old game. The coder and deployer prompts now ask for a server that fails on a taken port (`allow_reuse_address = False`, a clear message, exit code 1). A connect, not a bind, is the test: on Windows a bind with `SO_REUSEADDR` succeeds on a port in use.
- Without a start command (old projects, answers without the new fields) code derives one from the smoke command: the same command without a check option (`python -m shop --check` gives `python -m shop`), `derived: true`. From `python -c ...` nothing is derived: the start command stays empty, the guide says so, and the check does not fail for it. A project deployed before the run guide existed gets its guide on the next Check again.
- Replies: one line with the number of files, the check result and the deployer's `notes` cut to about two sentences; problems as a list of at most five with a count of the rest. The full notes are in `data.notes`.
- `check`: run the checks again (after a hand edit). `revise {feedback}`, `discuss {question}`.

**Limits:** Docker itself is not run (it may not be installed, and building images in the tool would be slow); DEPLOY.md has the commands. See ADR 0013.

**Grading hooks:** C1, C7 ("the deployment runs").
