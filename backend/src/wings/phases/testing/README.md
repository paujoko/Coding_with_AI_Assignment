# P5 Testing

**Requirement (PDF, P5):** generate tests, run them, report results. Tests come from requirements and design, not only from code. On failure, explain why, propose a fix, re-run.

**How it works**

- `generate {depth, guidance}`: the `tester` (mid, no tools) writes pytest files under `tests/` from the acceptance criteria; test names carry the requirement (`test_req_003_complete_a_task`). Files must parse. `depth` is `focused` (default, about one test per criterion) or `thorough`; the wing caps the number of tests from the acceptance criteria (`schema.py: test_limit`: focused criteria + 2 within 6 to 20, thorough twice the criteria + 4 within 12 to 50) and refuses more, so the model retries. Without `depth` the last one is kept (`content.depth` of `test-gaps`). The prompt forbids large data, sleeps and real servers unless a requirement is about serving pages (ADR 0018).
- `gaps`: the tester lists every requirement its tests do not check fully (artifact `test-gaps`, saved on every generation).
- `run`: code and tests run for real in the Sandbox. Wings copies its pytest plugin (`pytest_events.py`, loaded as `-p _wings_events`) into the run; it writes one JSON line per event while pytest runs, so the results survive a run that is stopped (`domain/testreport.py: parse_events`; JUnit XML is the fallback when the plugin wrote nothing). Each failure carries its project lines (`where`: path, line, the code there, the line that raised last) and each test its file (`path`). A file that cannot be imported is one `error` result named after the file, with its line. A test that runs longer than `TEST_LIMIT` (30 s) ends the run: it is an `error` that names the limit, and later tests do not run. Nothing comes from a model. Artifact `test-report` with counts, per-test results and `verified` (REQ id -> worst outcome, then `apply_gaps`: a tester's gap turns `passed` into `partial`, a coder's deviation gives `not_met`; only `passed` counts as verified).
- `probe {limit}` ("Inject bugs"): only after a green run on the current code and tests. `domain/mutation.py` picks `limit` small bugs (default 8, at most 20; deterministic, one changed line each), the tests run once per bug in the Sandbox, and the artifact `test-strength` (`reports/test-strength.md`, author `system:mutation`) says per bug: `caught` (which tests failed, which REQ ids), `survived` (all tests passed) or `invalid` (the run stopped before the tests or hit the time limit; not counted). Score = caught / (caught + survived). No model is asked. A surviving bug becomes a next step that opens `generate` with guidance for the missing test. The result goes out of date with code and tests like the test report (`domain/trace.py: strength_results`). Details: `docs/code/wings.md`, "Injected bugs".
- `explain`: the `debugger` (frontier) gets the failures with their lines first (`describe_failures`), then the earlier attempts of this fix loop, then only the test files the failures run through (plus `conftest.py`; the others are named) and all the code. It says which one is wrong. A wrong test is fixed in this phase (new test revisions, run again). A code bug becomes a next step "Send the fix to Code generation": codegen `revise` with the fix, the failing tests with their lines and the earlier attempts.
- Fix loop memory (`domain/fixloop.py`, ADR 0019): every `explain` adds an attempt (failing tests, cause, diagnosis, fix, files changed) to the artifact `fix-log` (kind `fix_log`, `reports/fix-attempts.md`, author `system:fixloop`). The next `run` records which tests still fail after it. The debugger and the coder read this history and are told not to repeat a fix that did not help; a test that fails after every attempt (two or more) is named as stuck. A green run or `generate` retires the log.
- `discuss {question}`.

**Demo for C7:** `probe` on the demo to-do program injects 8 bugs and reports which ones the generated tests catch (`tests/phases/test_testing_probe.py`, real pytest runs). `tests/phases/test_testing.py` injects one bug by hand, shows a test failing, sends the fix to code generation and shows the tests passing again.

**Limits:** the Sandbox runs with the developer's user rights (ADR 0013). Timeout 120 s per run, 30 s per test (`TEST_LIMIT`, a timer thread in the plugin; it ends the whole run, so later tests are not reported); per injected bug four times the last green run, at least 10 s. `probe` saves an artifact, so on an approved phase it reopens the phase (run it before approving). Surviving bugs can be equivalent changes that no test could catch.

**Grading hooks:** C1, C7.
