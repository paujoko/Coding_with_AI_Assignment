# Frontend

React 18, TypeScript (strict), Vite 6, Vitest 3. Code: `frontend/src/`. Visual system and rules: `design.md`.

## Structure

| `api/client.ts`, `api/types.ts` | typed fetch wrapper; types mirror backend DTOs; errors become readable `ApiError` messages |

## Behaviour worth knowing

- New actions in a wing need no frontend change: the composer renders a field per input property by its schema type (text, number, checkbox, select for enums, one-per-line list for arrays). The `answer` tab is only shown while a phase waits for answers.
- New artifact kinds need a view component and a branch in `PhaseWorkspace.tsx`; unknown kinds fall back to showing their text. Order in the results panel: the run guide, then verdicts (consistency, changes, review, test results, injected bugs, deployment check), then diagrams, then files.
- Next steps: `data.next_actions` of the newest agent message become buttons under it. A step for this phase without input runs at once; any other step opens its phase with the input in the composer and that action selected (`App.tsx` keeps it as `prefill` until the action ran), so the developer reads the proposal before sending it.
- Changes carried through the phases (API 9): `App.tsx` loads `GET /changes` with the phase data of Maintenance (`api.changes` fills every missing field and returns an empty list when the route is missing, so an older backend shows Maintenance as before). The results panel of Maintenance starts with the `ChangeTracker` of the newest change: an open one with its steps and buttons, a completed one as its receipt. Below it the consistency report, then all changes as collapsed rows.
- The tracker's buttons: the primary one does one step and is named for it ("Update the design" calls `advance` with `approve: false`, so the phase waits for the developer; "Approve the tests" calls it with `approve: true`; open questions and failed checks show the backend's reason and "Answer in ..." or "Open ..." instead). "Carry it through" loops `advance` with `approve: true` while `stopped_reason === null` and the change is open, at most 12 calls. After every call the project, the phase data and the trace are loaded again. The whole run is one `guarded` stretch, so navigation is off as during any agent action; a refused request (409, backend unreachable) is shown in the tracker and the project is loaded again. "Stop after this step" ends the loop when the running phase has answered; a request in flight is never cancelled.
- Maintenance outside the tracker: an empty conversation shows three ways in (`MaintenanceStart`; a change or a bug selects `change` and puts the cursor in the input, the check runs at once). The answer that created a tracked change (`data.change`) is shown without the lines the tracker repeats, and its next-step button is not primary. While a change is open the dock shows `ChangeDockNote` instead of the approval card, the phase badge and the sidebar say "Change 2 of 6", and in every other view one strip above the page ("Change #1: step 3 of 6, next: Code generation", **Open the change**) leads back. On a phone Maintenance opens on Results while a change is open.
- Trace navigation: a requirement's "In ..." links open the diagram in its phase; a diagram's covered IDs open the requirement and highlight it; a matrix row and "Follow REQ-..." under a requirement open that requirement's page in Traceability, which links on to every artifact in its phase and back to the requirement.
- Run it: when everything up to Deployment is approved (`readyToRun` in `lib/status.ts`), the next-step card of an approved step offers **Run it**: the primary button on Deployment ("The program is ready to run."), a secondary one elsewhere. It opens Deployment with `focus.artifact = "run-guide"`; the card scrolls into view and lights up once. On Deployment the button needs a `run-guide` artifact.
- Inject bugs: with a green test run in a Testing step that is not out of date, **Inject bugs** runs `probe` at once with its default input (like a re-run button). It sits on the next-step card while Testing waits for review and no bugs were injected for the latest run, and in the head of the test results; afterwards "Inject bugs again" sits in the head of the injected bugs. The backend applies the same rule and refuses otherwise. `api.trace` passes `strength` through as it comes: missing on an older backend, `null` when out of date or never run.
- While an agent works, every way to another phase is disabled (pipeline, view switch, project list, trace links, requirement chips), so a result always lands in the phase and project that asked for it. As a second guard, `App.tsx` keeps what the screen shows in a ref and drops any response that arrives for another project or phase (slow loads, quick clicks).
- If "Create and start" fails at the start step, the project exists and the description waits in its start composer.
- Selection groups (view switch, diagram tabs, composer actions) are buttons with `aria-pressed`, not ARIA tabs.
- Nothing typed is lost on failure: the composer clears the moment the developer sends (as chat apps do) and puts the text back if the backend refuses the action, unless the developer typed something new meanwhile; editors keep their draft when a save fails. Before s03 the text stayed in the box for the minutes an agent worked, which invited a second send.
- While an agent works, the progress line shows the time since the start (`useElapsed` in `Conversation.tsx`). If the project reports a `running` action this page did not send (sent before a reload, or in another tab), `App.tsx` shows that it is still running, disables sending, and asks `GET /projects/{id}` every 2 s until it has finished.
- Declared gaps: the results panel lists `known_gaps` artifacts with their requirement chips; the trace and the consistency table show `partly tested` and `not met` in amber; the test report names the requirements that do not count as verified despite passing tests.
- `GET /health` reports `api_version`; when it differs from `API_VERSION` in `api/client.ts` the app shows "The backend runs older code than this interface". `api.trace` fills missing fields with defaults, so an older backend cannot crash a view.
- Documents: uploaded as soon as they are added (like a chat app), sent as ids with the next message. On the start page files wait until the project exists, then go up before P1 starts. The results panel lists every document of the project.
- Downloads: requirements as `requirements.md`, each diagram as its `.puml` source, each generated file under its name, all files of a phase as one text file.
- Start page folder: `NewProject` asks `onSuggestFolder(name)` (`api.defaultFolder`, `GET /system/default-folder?name=<project name>` returning `{"path": ...}`) at once and again 350 ms after the name derived from the description changed. Typing in the field or choosing with Browse ends the suggestions. If the call fails (older backend) the field stays empty and typing works. Without a folder the project cannot start: the send button carries `aria-disabled` and a tooltip that names what is missing ("Describe the software first", "Choose a project folder first"); a click or Enter then puts the cursor in the folder field and shows one amber line.
- Folder: the banner above the step appears when the folder has hand edits or cannot be reached, and opens the Folder view. A project without a folder (made before the folder was required) gets one banner, "This project has no folder yet" with "Choose a folder", which opens the same view. A message no agent wrote carries `data.speaker` ("Folder sync, checked by code"); the conversation shows that name instead of the phase's agent, with the words "checked by code" replaced by the label. Its next steps (update the design from the code, or the code from the design) work like an agent's. A message with `data.drift` shows "Resolved since" instead of its steps once `GET /design-check` says design and code agree.
- Code generation asks `GET /design-check` with its phase data. When the phase is out of date but the code still matches the current class diagram, the next-step card says "Still fits" and offers Approve; when they differ, it lists the differences and makes "Request changes" the primary button (session s04: the generic "approve it again if it still fits" confused Ben after a design update from the code).
- Default action: once a phase has output, the composer selects Revise, or the phase's re-run step when it has no Revise (Testing: Run tests); an out-of-date phase with a re-run step (Run tests, Check again) selects that and offers it as the primary button on the next-step card. Session s04: "run the tests" typed with Write tests selected wrote new tests twice.
- Request changes selects Revise (or Write tests), puts the cursor in the input box, highlights the box and says on the card what to do; it ends when the developer sends or presses it again.
- Fonts are bundled (`@fontsource/host-grotesk`, `@fontsource/jetbrains-mono`); the app makes no request outside its own backend.
